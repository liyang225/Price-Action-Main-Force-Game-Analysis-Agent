# 分析流水线全程驻内存，收盘一次性序列化落盘

原始设计文档描述"返回的 JSON 文本以字符串/字典形式驻留在内存，实时 json.loads 解析后被流水线各环节直接使用；本地文件写入是终点动作——把整条分析记录一次性序列化保存，中间没有任何'写文件 → 读文件'的环节"。

这个原则有四个来源：PA_Agent 的"程序预填节点"模式、富途接口的内存对象返回（不落盘）、避免并发写入竞争、以及让每一条分析记录的输入完整可复现（一次写入即快照）。

## 例外：两类跨进程重启状态

**情绪台账**（每板块每日的情绪周期位置与指数值）必须跨交易日持久化。情绪有惯性，今日值以昨日值为基准加减，若进程重启就丢失；台账是一等公民的领域状态，不是流水线副产品。因此情绪台账每日收盘后单独持久化，不受"流水线内部不落盘"约束。

**分析材料缓存**（当日新闻、主体目的、博弈信号等）是日级共享状态——盘中多次分析（多个个股或两个决策点）共享同一份，避免重复 API 消耗。它在当日内跨多次决策存活，收盘归档。这同样是例外，但它的写入只发生在填充阶段（后台任务），读取发生在决策阶段，两者严格隔离，不存在流水线环节内部的"写完再读"。

## 拒绝的方案

- **每个分析步骤输出存为临时文件，下一步骤读入**：增加 IO 延迟，引入文件锁竞争，中间格式版本管理复杂，且单步失败后无法原子回滚。
- **使用 SQLite 作为流水线中转**：过重，中间记录没有审计需求，收盘后的最终记录才需要持久化。
